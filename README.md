# **Elite Dangerous High-Performance Rust Router**

This project provides a web-based, long-range route planner for Elite Dangerous, featuring a highly-optimized Rust backend for A\* pathfinding. The entire data processing pipeline and server are built in Rust for maximum performance, memory safety, and maintainability.
**Core Features:**

* \**High-Performance A* Search:\*\* A memory-efficient, unidirectional A\* search algorithm capable of plotting optimal long-range routes (e.g., Sol to Colonia) in seconds.
* **Intelligent Heuristics:** The pathfinder correctly prioritizes neutron star and white dwarf boosting and includes smart fuel management to plot safe, efficient routes that avoid dead ends.
* **Zero-Copy In-Memory Cache:** At startup, the server memory-maps a pre-computed binary cache (starmap.rkyv) for near-instantaneous access to the entire star map, resulting in a low memory footprint (~15 GiB) and fast startup times.
* **Parallel Data Processing:** Both the initial database creation and the cache generation are parallelized with Rayon to leverage all available CPU cores, dramatically reducing processing time.

## **Project Structure**

This project is structured as a single Rust package with a shared library and multiple binaries, following standard Rust conventions.

* src/lib.rs: The core library crate (ed-router) containing the shared astar and cache logic.
* src/main.rs: The main binary for the Actix web server (api-server).
* src/bin/import\_starmap.rs: A binary for importing the raw star data dump into an SQLite database.
* src/bin/cache\_generator.rs: A binary for processing the SQLite database into the optimized rkyv cache file.
* index.html: The single-page frontend user interface.
* starmap.db: The SQLite database (generated by the importer).
* starmap.rkyv: The binary cache for fast startups (generated by the cache generator).

## **Build & Run Instructions**

This guide provides a complete walkthrough from a clean environment to a running application.

### **Step 1: Prerequisites**

You need to have the Rust toolchain installed. If you don't have it, install it via [rustup](https://rustup.rs/).

You will also need a C compiler for the bundled rusqlite dependency. This is typically pre-installed on Linux and macOS. For Windows, you may need to install the [Microsoft C++ Build Tools](https://www.google.com/search?q=https://visualstudio.microsoft.com/visual-cpp-build-tools/).

### **Step 2: Get the Star Data**

Download the **galaxy.json.gz** file from the [Spansh Galaxy Dumps page](https://spansh.co.uk/dumps).

### **Step 3: Build the Data Pipeline (One-Time Setup)**

These steps are performed from the root directory of the project. Use the --release flag for optimized performance.

1. Create the SQLite Database:
   This command reads the massive gzipped JSON file and populates a local SQLite database. It will take a considerable amount of time.
   ```
   cargo run --release --bin import_starmap -- /path/to/galaxy.json.gz /path/to/created/starmap.db
   ```

2. Create the Binary Cache:
   This command reads the SQLite database and creates the highly optimized starmap.rkyv cache file for the server.
   ```
   cargo run --release --bin cache_generator -- /path/to/created/starmap.db /path/to/created/cache/starmap.rkyv
   ```

### **Step 4: Build and Run the Application**

Once the database and cache are built, you can run the API server.
```
cargo run --release -- /path/to/created/starmap.db /path/to/created/cache/starmap.rkyv
```

The server will start on http://localhost:8080. Open this address in your web browser to use the router.

## **API Endpoints**

* **GET /api/search?name=\<query\>**: Performs a fast, full-text search for system names.
* **POST /api/route**: Accepts a JSON body with route parameters and returns the calculated path.

## **How the High-Performance Search Works**

Finding the shortest path in a graph containing over 42 million systems is a significant computational challenge. This router uses a combination of pre-computation, memory-mapping, and carefully chosen data structures to solve it efficiently.

The process for a single API request is as follows:

1.  **Pre-computation (`cache_generator.rs`):** The key to performance is doing most of the heavy lifting offline. The cache generator processes the entire SQLite database and creates a single `starmap.rkyv` file. This file contains a `Vec<SystemPoint>` where all systems are **pre-sorted by their unique `system_id`**. This sorting is critical for the next step.

2.  **Memory-Mapping (`mmap`):** When the server starts, it does **not** load the entire multi-gigabyte cache file into RAM. Instead, it uses `memmap2` to map the file directly into virtual memory. This provides two massive benefits:
    * **Low RAM Usage:** The operating system handles paging the necessary parts of the file into physical RAM as they are requested. This means the router can run on a machine with less RAM than the size of the cache file.

3.  **Fast ID-to-Index Translation:** When an API request arrives with `start_id` and `end_id`, the server needs to find the location of those systems in the memory-mapped slice. Because the data is pre-sorted by `id`, it can perform a **binary search** (`O(log n)`) directly on the memory-mapped data. This is extremely fast and avoids the need for a large `HashMap<i64, usize>` in memory, saving gigabytes of RAM.

4.  **Index-Based A\* Search:** Once the start and end `usize` indices are found, the A\* algorithm begins. All internal pathfinding logic operates exclusively on these indices. Accessing a system's data (like its coordinates or star features) is a simple `O(1)` slice lookup (`points[idx]`), which is the fastest possible operation.

5.  **Spatial Lookups with R-Tree:** To find all neighboring stars within a ship's jump range, iterating through millions of systems would be too slow. An `RTree` is built at startup containing the 3D coordinates of every system. This data structure allows for incredibly fast spatial queries (e.g., "find all points within this radius"), making the neighbor-finding step of the A\* search efficient.

6.  **Intelligent Heuristics:** The A\* algorithm's cost function is weighted to heavily favor jumps that use neutron stars or land at another neutron star, guiding the search toward the "neutron highway" and producing optimal long-range routes much faster than a simple distance-based heuristic.

This combination of techniques allows the router to perform complex, fuel-aware pathfinding across the entire galaxy with minimal memory overhead and extremely high speed.
